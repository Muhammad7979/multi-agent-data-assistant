### Git-related absence matters

A `.git/` directory would hold repository history and tracking metadata. It is absent here. Do not infer that files are tracked merely because they are in a project folder.

A root `.gitignore` is also absent. The actual `.venv/.gitignore` contains `*`, which ignores contents within that directory if Git is used. It does **not** ignore the root `.env`. Before a future first commit, review ignore rules and local secrets yourself. No ignore configuration was changed in this task. Ignoring a path also does not untrack something already committed.

## The actual pyproject.toml

```toml
[project]
name = "data-agent"
version = "0.1.0"
description = "Add your description here"
readme = "README.md"
requires-python = ">=3.14"
dependencies = []

[project.scripts]
data-agent = "data_agent:main"

[build-system]
requires = ["uv_build>=0.12.17,<0.13.0"]
build-backend = "uv_build"
```

**WHAT?** A TOML configuration file. Bracketed headings group related settings; strings are quoted and lists use square brackets.

**WHY?** Tools need an agreed place to find your project's identity, compatibility, dependencies, and installation instructions.

**WITHOUT IT?** A standalone Python file could still run, but uv would no longer have this project's definition.

| Actual line/section | Meaning |
| --- | --- |
| `[project]` | Standard Python project metadata begins here. |
| `name = "data-agent"` | Distribution/project name used by packaging tools. It is not necessarily the import name. |
| `version = "0.1.0"` | Your application's release version, not Python's version. |
| `description = ...` | Placeholder summary. It does not affect the greeting. |
| `readme = "README.md"` | Points to the root README for longer package description content, not `docs/README.md`. |
| `requires-python = ">=3.14"` | Declares Python 3.14 or newer as compatible. It neither installs Python nor selects exactly 3.14.7. |
| `dependencies = []` | No third-party runtime dependencies are declared. Python's built-ins and standard library need no entry here. |
| `[project.scripts]` | Defines commands to generate when installing this project. |
| `data-agent = "data_agent:main"` | Create command `data-agent`; import `data_agent`; call its `main` function. The colon separates module from callable. |
| `[build-system]` | Says how packaging tools should build/install this source project. |
| `requires = ["uv_build>=0.12.17,<0.13.0"]` | Build-time package requirement: at least 0.12.17, below 0.13.0. This is not a requirement on the uv CLI version. |
| `build-backend = "uv_build"` | Selects the Python build backend that understands this package layout. |

**IMPORTANT NOW:** there are three related names: distribution `data-agent`, import package `data_agent`, command `data-agent`. Hyphens are fine in command/distribution names; this Python import uses an underscore.

The build backend helps turn source into an installable package, including command metadata. uv invokes it; the interpreter does not run the backend each time it calls your greeting. Normal isolated builds can obtain build requirements separately from runtime dependencies. The existing environment lists only the `data-agent` distribution, not `uv_build`. [Official build backend documentation](https://docs.astral.sh/uv/concepts/build-backend/).

Not currently present: `[dependency-groups]` (for development tools, for example), `[project.optional-dependencies]`, or `[tool.*]` settings. There are no declared development dependencies. A build dependency is not a development dependency group.

Mental analogy: `pyproject.toml ≈ composer.json`. Both describe a project and its dependencies. Python's file also serves multiple build and tooling conventions; sections and command behavior are not Composer's schema. This starter has no Laravel-style routes, service container, HTTP entry point, or framework boot process.

## The actual uv.lock

```toml
version = 1
revision = 3
requires-python = ">=3.14"

[[package]]
name = "data-agent"
version = "0.1.0"
source = { editable = "." }
```

**WHAT?** A generated record of resolved dependency information.

**WHY?** A version range can allow many releases. Dependency resolution means selecting compatible versions that satisfy the project's requirements and the packages' own requirements. The lock preserves that result.

**WITHOUT IT?** A later resolution may choose a newer compatible release. Configuration alone does not preserve the previous selection.

Here, `version = 1` and `revision = 3` describe the lock format, not Python, uv, or your app version. `[[package]]` starts one package record. The only record is your local application, version `0.1.0`. `editable = "."` points to this project directory. No external runtime dependency versions are locked because none are declared. The build requirement remains in `pyproject.toml`; this lock is not a list of every tool involved in building.

Hypothetical example — these packages are **not** in this starter:

```text
My application
      ↓ directly requests
Package A
      ├── needs → Package B
      └── needs → Package C
```

A is a **direct dependency**. B and C are **transitive dependencies**: required indirectly. You might write only A in `pyproject.toml`; uv resolves all three and records their versions in `uv.lock`. Installed copies live in the environment; lock entries are only information.

Normally commit this application's lock, review changes, and let uv write it. Adding/removing dependencies, changing compatibility, or requesting upgrades can change it. Re-running a lock operation does not mean every package must be upgraded; existing compatible choices can be kept. [Official locking and syncing guide](https://docs.astral.sh/uv/concepts/projects/sync/).

Mental comparison:

```text
pyproject.toml ≈ composer.json   (declared requirements)
uv.lock       ≈ composer.lock   (resolved choices)
```

The formats are unrelated. uv's lock can account for multiple Python versions/platforms; it is not a copied environment or a standard pip requirements file. Reproduction still depends on compatible Python, available artifacts/build tools, and platform conditions. See [reproducing this project](04_PYTHON_RUNTIME.md#reproduce-this-project).

## The source and entry point

The complete `src/data_agent/__init__.py` is:

```python
def main() -> None:
    print("Hello from data-agent!")
```

A `.py` file contains Python source. Here, `__init__.py` also makes `data_agent` a regular package and supplies the module loaded by `import data_agent`.

- `def main()` creates a function called `main`. That name alone does not make Python run it automatically.
- The colon starts its body. Indentation defines the body; there are no PHP-style braces.
- `-> None` is a return type annotation: the function is intended to return no meaningful value. It is not runtime enforcement like a PHP return type declaration. Falling off the end returns `None`.
- `print(...)` is a built-in function. No dependency or import is needed for it.
- The function definition is a top-level statement. Importing this module defines `main`; it does not execute the indented `print` until the function is called.

There are no explicit imports, classes, assigned application variables, or `if __name__ == "__main__"` guard in this source. Learn that guard through the separate, clearly hypothetical [runtime example](04_PYTHON_RUNTIME.md#direct-execution-versus-importing).

The other source files, root `main.py` and the newly observed `agents/sql-analyst.py`, are empty. Neither implements startup behavior. A hyphenated filename can be executed by path, but `import sql-analyst` is not valid Python import syntax; normal import module names use identifiers such as `sql_analyst`. No filename was changed.

VERIFIED: importing `data_agent` with the environment interpreter finds this source file. Calling `data_agent.main()` prints `Hello from data-agent!`. Running the empty root `main.py` produces no output and exits successfully. The generated `data-agent.exe` exists and its installed metadata maps to `data_agent:main`; that launcher was not executed during inspection.
